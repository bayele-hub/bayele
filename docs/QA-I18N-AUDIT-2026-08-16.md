# Bayele — QA Audit: English / French Readiness (i18n)

**Date:** 2026-08-16
**Reviewer roles:** Principal Frontend & Design Systems Architect · Product Lead / TPM · QA & Chaos Engineering Lead
**Scope:** `apps/web` structure vs. a bilingual (French + English) requirement
**Verdict:** ❌ **Not established.** The app is a **single-language French build** with **no internationalization layer**. It cannot serve English today, and there is no structural seam to add it without a dedicated i18n pass. This is a **structural gap**, not a bug — nothing is "broken," but the requirement is unmet.

---

## 1. What "properly established for EN/FR" requires

A bilingual Next.js 15 App Router app needs five things. The audit checks each.

| # | Requirement | Present? | Evidence |
|---|---|---|---|
| 1 | An i18n library or dictionary system | ❌ No | No `next-intl` / `react-intl` / `i18next` in any `package.json` |
| 2 | Locale-aware routing (`/[locale]/…` or detection) | ❌ No | No `[locale]` segment anywhere under `apps/web/app` |
| 3 | Externalized UI strings (message catalogs) | ❌ No | No `messages/` `locales/` or `dictionaries/` folder; **all** copy is inline |
| 4 | Dynamic `<html lang>` | ❌ No | `layout.tsx` hardcodes `<html lang="fr">` |
| 5 | Locale detection / switch (middleware + UI) | ❌ No | Middleware has no `Accept-Language` / `NEXT_LOCALE` handling; no language switcher |

Five of five missing. The app is French-by-hardcoding, not French-by-configuration.

---

## 2. Findings (severity-ranked)

### F1 — All UI copy is hardcoded French in components — **High (blocks EN entirely)**
Every user-facing string lives inline in JSX across at least: `(public)/page.tsx`, `(auth)/auth/page.tsx`,
`(public)/legal/page.tsx`, the `(app)` dashboards, and directory stubs (e.g. "Créateur", "Séquestre",
"Connexion", "Lancer une campagne", "Nano-créateur"). There is no key→translation indirection, so English
is impossible without editing every component. This is the root gap; everything else follows from it.

### F2 — No locale routing or default-locale strategy — **High**
There is no `/fr` or `/en` (or hidden-default) URL structure and no `[locale]` segment. Google would index
only one language, and a shared WhatsApp link can't carry a language preference — material for a market that
spans Francophone-primary (CM, GA, CI) but wants English reach.

### F3 — `<html lang="fr">` is static — **Medium (a11y + SEO)**
Screen readers and search engines are told every page is French even if English content were served. `lang`
must be driven by the active locale.

### F4 — Metadata is French-only, not per-locale — **Medium (SEO)**
`title` / `description` in `layout.tsx` are a single French string. Bilingual SEO needs per-locale metadata
and `hreflang` alternates so each language ranks on its own.

### F5 — Number / date / currency formatting is French-convention, hardcoded — **Medium**
Amounts render as "450 000 FCFA" (French thin-space grouping) and the footer year uses the default locale.
English users expect "450,000 FCFA". These should go through locale-aware `Intl.NumberFormat` /
`Intl.DateTimeFormat`, not literal strings. (Currency stays FCFA — XAF/XOF — in both languages.)

### F6 — Legal hub exists in French only — **Medium (compliance)**
`/legal` (CGU, Séquestre, Confidentialité, OHADA) is French-only. If English users can sign up and accept
terms, an English rendering is needed — and legal copy should be reviewed per language, not machine-translated.

### F7 — Enum/status → label mapping is inline French — **Low-Medium**
Role and status labels ("Nano-créateur", "Consultant stratégique", campaign/escrow statuses) are mapped to
French strings inside components. These belong in the message catalog keyed by the enum value, so the DB stays
language-neutral (it already stores neutral enums — good) and the UI localizes the display.

### F8 — Auth-country UX is fine, but copy isn't localized — **Low**
The `/auth` funnel's country/dial-code logic (CM/CI/GA) is locale-independent and correct. Only its labels
("Créer un compte", "Numéro Mobile Money", validation/error text) need externalizing.

**Good news / what's already right:** the **data layer is language-neutral** — enums, statuses, and IDs carry
no language, and user-generated content (categories, briefs) is stored as-is. So i18n is a **presentation-layer**
addition; no schema or RLS change is required. That keeps the remediation contained to `apps/web`.

## 3. Recommended target architecture

For Next.js 15 App Router with exactly two locales, the standard, robust choice is **`next-intl`** (first-class
App-Router + Server Component support, minimal boilerplate) composed with the existing Supabase middleware.

```
apps/web/
├── i18n/
│   ├── routing.ts          # locales: ['fr','en'], defaultLocale: 'fr'
│   └── request.ts          # loads the active locale's messages
├── messages/
│   ├── fr.json             # source of truth (market-primary)
│   └── en.json             # English translations
├── middleware.ts           # next-intl locale middleware + Supabase auth, composed
└── app/
    └── [locale]/           # every route moves under here
        ├── layout.tsx      # <html lang={locale}>, NextIntlClientProvider
        ├── (public)/…
        ├── (auth)/…
        └── (app)/…
```

Key decisions to lock before building:

- **Default locale = French** (market-primary). Recommended URL strategy: **hide the default prefix** —
  `/` and `/creators` stay French; English lives at `/en`, `/en/creators`. Best of both: clean canonical
  French URLs for WhatsApp shares, first-class English for reach. (next-intl `localePrefix: 'as-needed'`.)
- **Library:** `next-intl` (recommended) vs. a **zero-dependency custom dictionary** (lighter, but you
  hand-roll routing, formatting, and the provider). For FAANG-grade correctness and future locales, next-intl.
- **Translation source of truth:** author in **French**, translate to English. Legal copy gets a **human**
  legal review per language — do not ship machine-translated terms.

---

## 4. Remediation plan (presentation-layer only)

1. **Install & wire** `next-intl`: `i18n/routing.ts`, `i18n/request.ts`, compose its middleware with the
   Supabase auth middleware (order: locale first, then auth).
2. **Restructure routes** under `app/[locale]/`; make `layout.tsx` emit `<html lang={locale}>` and wrap in
   `NextIntlClientProvider`; per-locale `generateMetadata` + `hreflang` alternates.
3. **Extract every string** into `messages/fr.json` (keys by area: `nav.*`, `hero.*`, `escrow.*`, `auth.*`,
   `legal.*`, `roles.*`, `status.*`), then produce `messages/en.json`.
4. **Localize formatting** — route amounts/dates through next-intl formatters; keep FCFA/XAF-XOF.
5. **Add a language switcher** in the nav + footer (persists `NEXT_LOCALE`).
6. **Localize enum/status labels** via `status.*` / `roles.*` keys.
7. **Verify:** `/` renders French, `/en` renders English, `<html lang>` flips, `Accept-Language` picks the
   right default, no untranslated keys (add a CI check that `en.json` and `fr.json` have identical key sets).

Estimated as one focused milestone; **no database, RLS, or escrow change** is involved.

---

## 5. Bottom line

The foundation is clean and i18n-friendly (language-neutral data, one Next app, centralized components), but
**English/French is not established** — it's French-only by hardcoding. Establishing it is a contained,
presentation-layer milestone. The one thing to decide before implementing is the **URL strategy + library**
(section 3); everything else follows a standard path.
