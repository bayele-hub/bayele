## 2. Findings and fixes — production spec (v1.1.1 → v1.1.2)

Severity: **Critical** = blocks build or moves money unsafely · **High** = breaks a core flow or leaks data · **Medium** = silent malfunction · **Low** = correctness/hygiene.

### A. `transition_escrow()` referenced everywhere, defined nowhere — **Critical (non-buildable)**
`handle_sokoclick_invoice_paid()` (§4.2) and `verify_proof_of_post()` (§5) both call
`transition_escrow()`, but no version of the spec defined it. The escrow subsystem — the heart of the
product — could not run.
**Fix:** Added §3.3 with a full definition: an explicit allowed-transition table, a `FOR UPDATE` row
lock to serialize concurrent release/refund attempts, a mandatory `escrow_audit_log` write on every
hop, and `REVOKE` from `anon`/`authenticated`. It is now the single, only mutator of escrow status, so
the audit trail is closed by construction.

### B. RLS enabled with no policy on the role-profile tables — **High (public marketplace dead on arrival)**
`creator_profiles` and `consultant_profiles` had `ENABLE ROW LEVEL SECURITY` but **zero policies**. In
Postgres, RLS-on + no-policy = deny-all. The public directory query in `bayele-home.md` joins these
tables, so an anonymous visitor would have seen an empty grid — the entire top-of-funnel, broken and
silently.
**Fix:** Added public-read policies for both (scoped to `active` profiles holding the matching role),
owner/admin management policies, a `user_roles` read policy, and a `campaign_creators` visibility
policy for the proof-review list (§3.2).

### C. `verify_proof_of_post()` had no authorization check — **High (self-approval / payout theft)**
The function is `SECURITY DEFINER` (bypasses RLS) and, exposed as an RPC, performed no check on the
caller. A creator could call it on their **own** proof, approve it, and drive their escrow to
`releasable` — the exact class of bug the §0 fixes were about.
**Fix:** The function now resolves the campaign owner up front and raises unless `p_actor` is the owner
or an admin, before mutating anything (§5). Added `REVOKE ... FROM anon`.

### D. Broken middle of the escrow state machine — **Medium-High (payouts can never fire)**
`handle_sokoclick_invoice_paid()` creates a **campaign-level, inbound** escrow row (no
`campaign_creator_id`). But `verify_proof_of_post()` searches for a **per-creator, `proof_pending`**
row — which nothing ever created. No payout could reach `releasable`.
**Fix:** Added `submit_proof_of_post()` (§5.1): on creator submission it records the proof, creates the
outbound per-creator payout row, and walks it `pending → held → proof_pending` (each hop via
`transition_escrow()`), landing exactly where the verifier expects it. Added an end-to-end money-path
diagram showing every arrow is an audited transition.

### E. `notifications` subsystem dropped from the canonical migration — **Medium**
Phase 1 (tech-stack §5) treats notifications as first-class and §2 of the spec references a Realtime
notification bus, but §3.1's migration omitted the table entirely.
**Fix:** Carried `notifications` + its partial unread index into §3.1, enabled RLS, and added
recipient-only read/update policies (§3.2). Writes remain service-role/definer only (single `notify()`
write path).

### F. Wrong currency for Côte d'Ivoire — **High (wrong currency for a launch market)**
`SokoClickEngine` hardcoded `currency: 'XAF'`. CI is in UEMOA and uses **XOF**; only CM/GA (CEMAC) use
XAF. Every Ivorian invoice would carry the wrong ISO currency, even though both are colloquially "FCFA."
**Fix:** Currency is derived from country — `CI → XOF`, `CM`/`GA → XAF` (§4.1), with a comment warning
they must never be mixed on one invoice.

### G. Invoice needs an email that isn't modeled — **Low-Medium**
The SokoClick SDK sends `business.email`, but no email exists anywhere: `profiles` stores `phone_e164`
only and `business_profiles` had no email column.
**Fix:** Added `business_profiles.billing_email` as the invoice contact of record (§3.1); flagged in
SKILL.md §8 that onboarding must collect it.

### H. `middleware.ts` in the wrong location — **Medium (RBAC gate silently inert)**
Both prior specs placed `middleware.ts` inside `app/` (the production spec at `app/middleware.ts`, the
tech-stack inside `app/(app)/`). Next.js only runs middleware at the project/`src` root; anywhere else
it never executes, silently disabling every route gate.
**Fix:** Corrected to the app root in the spec's topology (§2) and in the tech-stack tree and §3.4
snippet; verification matrix and SKILL.md invariant #1 reinforce that RLS — not middleware — is the
real boundary regardless.

**Verification matrix (§8) expanded** with dedicated rows for A, B, C, D, and F — each stated as a
concrete failing-test-first check, consistent with the doc's existing "nothing says PASSED" discipline.
